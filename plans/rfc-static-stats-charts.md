# RFC: Static stats charts for a consuming site

Status: IN PROGRESS. Implementation and the recommended API decisions were authorized by the maintainer. The palette comparison was approved on 2026-10-28. Execution targets one stable 9.0.0 release after verification; the intermediate release candidates in §11 are not required.
Date: 2026-10-27
Scope: OpenChart library (core, engine, vanilla, the three wrappers), documentation and gallery only. The consuming site's own components, data layer, copy and tests stay in its repository.
Related: [v9 plan](v9-chart-clarity-and-annotation-ux.md), [v9 execution checklist](v9-execution-checklist.md), [desktop chart and GeoMap RFC](done/rfc-desktop-chart-and-geomap-design.md) (the format this document follows).

## 1. Recommendation and approval boundary

A static site (an Astro build) is adopting OpenChart for every data mark on its pages: full figures, a React island, and small in-table marks (a dot with an interval whisker, a count bar, a sparkline) that must share one scale down a column of dozens of rows. The maintainer decided that each gap between the site's design mocks and what OpenChart renders is built in OpenChart, not worked around in the site with hand-written SVG or post-processing, and that v9 stable is cut once those gaps close. Until then the site depends on the npm `next` prerelease.

Approve a staged program of three buckets. All of it ships before `9.0.0` stable; the first two buckets are additive and the third changes a default.

| Bucket | Contents | Release policy |
| --- | --- | --- |
| S1: static platform | A static renderer that builds its own element tree instead of swapping `globalThis.document` for happy-dom, with a fresh id scope and mark state per static render (live mounts keep sharing one page-level scope) so calls are reentrant and worker-safe (§7.1); self-contained output with a theme attribute and no document-wide `<style>` leakage so a light and a dark SVG can be inlined in one page (§7.2); `interactive: false` so legend buttons and the tab stops on note markers and footnotes never reach static output (the note marker's dot and number stay); `measureText` passthrough; static rendering of `barlist` (§7.7). | 9.0. The DOM swap goes; `happy-dom` stops being required by `@opendata-ai/openchart-vanilla/static`. Output for existing specs is byte-compared against the happy-dom path during the transition, after the intended changes in §12 are normalized. |
| S2: grammar | `encoding.description` (Vega-Lite's channel) rendered as `aria-label` and a per-mark `<title>`; `data-mark` and field-derived identity attributes on data marks; the `errorbar` mark (Vega-Lite spelling, explicit bounds); a one-point series drawn as a dot, never a zero-length path; `display`, `a11y` and `frame` on `LayerSpec`; vertical bars on a continuous temporal x scale so a column chart and a line chart share one axis and one reference line; fixed `frame` gutters so their plots align; bar list `group`, `sort`, value domain, reference lines, `labels` and `a11y`; `labels.content` for bar and range segments; `a11y.table: false` and `onMarkFocus` so a host can own the island's data table and live region (§7.3–§7.9). | 9.0, additive. Omission reproduces the current output except where §12 lists an intended change. |
| S3: defaults | The default light categorical palette fails WCAG 1.4.11 (3:1) for three of six colors against white and near-white surfaces (§7.10). Retune it in the major, with before/after plates, or record that the maintainer prefers hosts to supply palettes. | 9.0 only with the maintainer's approval on plates; otherwise dropped, not shipped as an opt-in. |

What this RFC does not ask for: a static HTML renderer for the `table` type, static `sankey` or `graph`, a second spec grammar, a React server component, site data fetching, the site's stats wire schemas or copy (§11). The site's tables are its own HTML (links, `<details>`, en dashes) with OpenChart marks inside cells; nothing in the mocks draws a sankey or a graph.

Source observations were checked on 2026-10-27 against `main` at `9.0.0-rc.2`. Symbol names are cited rather than line numbers.

## 2. Product problem, evidence, and success

### Who reads these charts

| Person | Job | Current friction | Desired outcome |
| --- | --- | --- | --- |
| Engineer choosing a stack | Which stacks work, how sure is that, is it alive | A bare percentage hides sample size; a green/red palette judges | Every rate carries its interval and `n`; popularity and success stay in separate columns |
| Stack author | Did my change break it; where does it break | A hover-only chart hides the evidence from a screenshot or a text browser | Static SVG with per-mark titles and a data table; markers labelled with their date |
| Site build | Render two themes of every figure for a hundred entries in under three minutes, inside a 120,000-byte gzip budget per page | The static renderer swaps a global `document`, forbids reentrancy, requires happy-dom, and its `<style>` block applies document-wide | A renderer that is a pure function of (spec, options), safe to call from any worker, with compact self-contained output |
| Screen reader user | Read the finding once, then the values | OpenChart's hidden data table would duplicate the site's own `<details>` table | `role="img"` plus the figure's finding sentence; no second table |

### Evidence from the mocks and the site plan

The mocks (`mocks/Home.dc.html`, `Browse.dc.html`, `Trending.dc.html`, `Fragment.dc.html`, `Stack Detail.dc.html`, with `stacks-data.js`) draw 50 distinct data-encoding elements, almost all as absolutely positioned `<div>`s computed in each page's `renderVals()`; four are inline SVG (`<polyline>` sparklines, one multi-line `<path>` chart). Seven more are computed but never bound to markup: the stack page's green-rate history line, its interval band polygon, a daily projects strip, rate and month ticks, dashed change markers and a history data table (`series()`, `ratePath`, `bandPath`, `projPath`, `rateTicks`, `monthTicks`, `markers`, `historyRows`). The site plan reads that as an export loss, keeps the history as the stack page's one island, and puts the weekly projects by preset beneath it. §5 inventories every element.

Two things the mocks never do, and the site must: carry a `<title>` per mark and a `data-*` identity on marks (the mocks have neither), and toggle between two spans without script (the mocks' toggles are React state). Both become OpenChart output or stay site HTML, per §5.

The site plan's binding line (its "What this plan may get wrong", 2026-10-27):

> the maintainers reversed "What doesn't fit" above. Every data mark on the site, in-table marks included, is OpenChart, and each gap between the design mocks and OpenChart (features, marks, chart types, static rendering of browser-only types, a static renderer that doesn't swap `globalThis.document`) is built in OpenChart itself, not worked around in the site; OpenChart's v9 is cut once those gaps close. Until then `apps/web` depends on OpenChart's npm `next` prerelease (the v9 release candidates, which the maintainers call stable), the one prerelease the site allows, and moves to stable 9.x when it ships. So `render.ts` uses `idPrefix` instead of renaming ids, and `RateMark`, `CountBar` and `Spark` render through OpenChart rather than hand-written SVG. The chart unit waits on an inventory of those gaps and the OpenChart work it produces; the data layer and the stats fetch don't depend on it.

The plan's four rules for every chart, which OpenChart must not undercut:

> - Green rates always carry their Wilson interval (4.2a's `lower` and `upper`) and `n` (the effective attempted sample 4.2a publishes as `sample`). A bare green-rate percentage never appears. [...]
> - Popularity and success are separate marks in separate columns. No page combines them into one score.
> - No chart uses green and red to judge a stack. Status colors appear only for a real status: a ledger run's `pass` or `fail`.
> - A total, share, rank or "others" bucket follows 4.2a's rule for totals and shares: over published cells only [...]

So the interval is data the site supplies (`lower`, `upper` fields), never something OpenChart computes; the rate mark must not default to `positive`/`negative` colors; and OpenChart computes no totals, shares or ranks for these figures (the `barlist` sort is the one ordering it applies, and only where the plan asks for a ranked list).

### Acceptance outcomes

1. `renderStaticSVG` is a pure function of its arguments: no global `document` or `window` swap, no module-level mutable state, no `happy-dom` requirement, reentrant, and byte-identical for the same spec and options across calls, call order, processes and worker threads.
2. Two static renders of one spec (light and dark) inlined in one HTML document render independently and correctly; every generated `id` and every reference form resolves inside its own figure when the caller passes a distinct `idPrefix`.
3. Every data mark's shape element in static output carries `data-mark`, its identity fields as `data-<field>` attributes and (when `encoding.description` is set) a `<title>` whose text is exactly the author's string; decorative marks carry none of these. Children of a `role="img"` root are presentational to assistive technology, so static output carries no per-mark `aria-label` (the `<title>` serves pointer tooltips and tests; the figure's name is the root's). No `<script>`, no `tabindex`, no `role="button"`, no animation class, no hidden data table. A live mount can keep keyboard navigation and drop its own data table (`a11y.table: false`) when the host provides one.
4. A point with an asymmetric interval, a one-point series, a stacked column with an absent segment, a line with gaps, a ranked bar list with groups and a reference line, and a two-chart figure sharing one x axis each render from a documented spec with no site-side geometry.
5. Every new option reproduces the 9.0.0-rc.2 output when omitted, except the intended changes in §12; each is listed with its story and reason.
6. The site's acceptance assertions quoted in §5.2 are satisfiable from OpenChart output plus site HTML, with the four test-string adjustments listed in §13 and nothing else.

## 7. Design

Each area names the spec surface (core types, JSON schema, `MARK_ENCODING_RULES`), the engine change, the vanilla change, the static-renderer change, wrapper parity, accessibility, theming, docs and the gallery story. Where an area adds nothing to one of those, it says so.

### 7.1 A static renderer without a global DOM (G1, G2, G5)

Today's path: `renderStaticSVG` → `getHappyDomWindow()` → assign `globalThis.document`/`window` → `resetSvgIdCounter(idPrefix)` → `compile*` → `renderChartSVG(layout, container, { animate: false, crosshair: false })` → `stripInteractiveElements` → inject `buildThemeStyleBlock` into `<defs>` → `new win.XMLSerializer().serializeToString(svg)` → restore globals. Every renderer creates nodes through `document.createElementNS`, directly or through one of eight local factories (§4), writes attributes, `textContent` and `.style`, and reads nothing back. That makes the DOM an element tree plus a serializer, and neither needs a global.

Design:

1. **Element factory.** `renderers/svg-dom.ts` exports

   ```ts
   export interface ElementFactory {
     svg(tag: string): SVGElement;      // SVG namespace
     html(tag: string): HTMLElement;    // barlist/table HTML, foreignObject content
     text(data: string): Text;
   }
   ```

   `createSVGElement(tag, factory?)` and `setAttrs` stay; `applyTextStyle` keeps writing through `.style` (see the `style` object below). `renderChartSVG`, `renderMapSVG`, `renderTileMapSVG` and `renderBarListSVG` take a `RenderContext` on their options object and thread it to `renderMarks`, `renderAxes`, `renderLegend`, `renderAnnotations`, `renderChrome`, `renderEndpointLabels`, `gradient-utils.ts`, `pattern-utils.ts` and the map/tilemap helpers. The default factory wraps `document`, so live mounts and existing tests are unchanged. The local factories in `map-renderer.ts`, `tilemap-renderer.ts`, `map-labels.ts`, `map-view-renderer.ts`, `map-camera.ts` and `barlist-renderer.ts` are deleted in favor of the context's factory. Renderers do change in this unit: every `document.` reference on the static path becomes `ctx.factory`, and that is the whole point of the sweep.

2. **Static node tree.** New `vanilla/src/static-dom.ts`:

   - `StaticElement`: `tagName`, `namespaceURI`, ordered `attributes: Map<string, string>`, `childNodes`, `parentNode`, `textContent` getter/setter, `setAttribute`, `setAttributeNS`, `getAttribute`, `hasAttribute`, `removeAttribute`, `appendChild`, `insertBefore`, `removeChild`, `firstChild`, `querySelector`/`querySelectorAll` for the selector forms the renderers use (tag, `[attr]`, `[attr='v']`, `.class`, descendant combinator), `classList` (`add`, `remove`, `contains`, `toggle`) and a `style` object with `setProperty`, `removeProperty`, `getPropertyValue`, `cssText`, and camelCase property assignment (`style.height`, `style.pointerEvents`) through a `Proxy`, serialized as the `style` attribute in declaration order with happy-dom's `name: value;` spacing. The static path writes `.style` in `applyTextStyle`, `svg-renderer.ts` (`svg.style.height`, `pointerEvents`), `renderers/marks.ts` (`renderTextMark`, `stampAnimationAttrs`), `renderers/chrome.ts`, `renderers/annotations.ts`, `renderers/endpoint-labels.ts`, `renderers/attribution-footer.ts`, `theme-tokens.ts::stampThemeProperties` and `barlist-renderer.ts`; a test enumerates these call sites by grep so a new one cannot bypass the proxy.
   - `StaticText`: `data`, `textContent`.
   - `serialize(node, { precision })`, written to match `XMLSerializer` as happy-dom 20.8 implements it, which is what rc.2 output is: the root carries `xmlns` (and `xmlns:xlink` when an `xlink:` attribute is present) before the other attributes; an element with no children self-closes as `<tag …/>`; attribute values escape `& " < > \t \n \r`; text nodes escape `& < >` only. The parity test normalizes that one token.

3. **Render context.** New `vanilla/src/render-context.ts`:

   Id format is pinned to today's strings: `ids.next('oc-clip')` yields `oc-clip-N` in the page scope and `<prefix>-oc-clip-N` in a prefixed scope (the hyphen `resetSvgIdCounter` inserts stays). Live mounts (`mount.ts`, `map-mount.ts`, `tilemap-mount.ts`, `barlist-mount.ts`, `sankey`, `graph`) build their context on `pageIdScope`, so ids stay unique across every chart on a page, which is what `svg-ids.ts`'s header requires; a static render builds `createIdScope(options.idPrefix)` and never touches the page counter. Without `idPrefix` the static scope is `ocs-<hash>`, an FNV-1a hash of the serialized spec and options (`static-render.ts::defaultIdPrefix`), so unprefixed static figures neither reuse the page scope's `oc-clip-0` nor collide with each other, and identical calls stay byte-identical. Every `nextSvgId` caller listed in §6 reads `ctx.ids`, as do `sankey-renderer.ts`'s gradient ids and `map-zoom.ts::clipIdCounter` (G5). `svg-ids.ts` keeps `nextSvgId(prefix)` as the page scope's function for one release and `captureSvgIdState`, `restoreSvgIdState` and `resetSvgIdCounter` are deleted (they exist only for the swap).

4. **`renderStaticSVG`.** Builds `createRenderContext({ factory: staticFactory, ids: createIdScope(idPrefix), interactive: false, precision })`, compiles with `measureText` forwarded (`CompileOptions.measureText` exists; `createMeasureFn` falls back to `estimateTextWidth`), renders into a `StaticElement` container and returns `serialize(root)`. No `createRequire('happy-dom')`, no `globalThis` assignment, no `rendering` flag, no `cachedWindow`. `happy-dom` leaves `vanilla/package.json`'s `peerDependencies` and `peerDependenciesMeta`. `stripInteractiveElements` is deleted: with `ctx.interactive === false` the voronoi overlay, crosshair and snap dots are never created. An unsupported spec (`table`, `sankey`, `graph`) throws `renderStaticSVG does not render "<type>"; supported: chart, layer, barlist, tilemap, geomap` instead of today's chart validation message (Q10).

5. **Options.** `StaticRenderOptions` gains

   | Option | Type | Default | Meaning |

   | `measureText` | `(text, font) => number` | `undefined` (estimate) | Forwarded to compile; a host with font metrics gets exact label fitting |
   | `precision` | `number \| null` | `3` | Decimal places for numeric coordinate attributes (`x y x1 y1 x2 y2 width height r rx ry cx cy dx dy d points transform viewBox`), applied in the serializer on that allowlist. `null` writes raw doubles. Three decimals is below the 0.01 tolerance the site's geometry tests use |

   `interactive` is not an option: static output has nothing to interact with, and the context field documents why no `tabindex`, `role="button"` or overlay appears.

The static renderer logs nothing and reads no environment variable.

The §8 site figures use marks and options rc.2 lacks, so their goldens are their contract. Wrappers: untouched. Docs: `docs/static-rendering.md` (new, U13) replaces the static paragraphs in `docs/dashboards.md` and the README; `docs/codebase-map.md` gains `static-dom.ts` and `render-context.ts`.

### 7.2 Self-contained themed output (G3, G4)

Problem: `buildThemeStyleBlock` emits a root rule and 22 class rules. In an HTML page a `<style>` inside an inline `<svg>` is document-wide, so the dark SVG's block restyles the light SVG beside it (whichever comes later wins). The site inlines two themes of every figure.

Design:

1. **Root attributes.** The static root gets `data-theme="light"|"dark"` from `layout.theme.isDark` and `id="<idPrefix>-oc-root"` when `idPrefix` is set (no `id` otherwise, so output for callers without a prefix is unchanged). Live mounts also stamp `data-theme` on the SVG (§7.9).

2. **Every rule in the block, and where its replacement lives.** Static chart and layer output drops the block; each rule's effect is written on the nodes that carry the class, from the same `ResolvedTheme` values the block resolves. `svg-dom.ts::applyRoleStyle(ctx, el, role)` holds the mapping in one table so the block and the inline path cannot drift (a test renders each role both ways and compares computed values under happy-dom).

   | Rule in `buildThemeStyleBlock` | Replacement in static output |
   | --- | --- |
   | `svg.oc-chart, svg.oc-map, svg.oc-tilemap, svg.oc-barlist { --oc-*: …; font-variant-numeric: tabular-nums }` | Root: `font-family` attribute from `fonts.family`; `style="font-variant-numeric: tabular-nums"` (no presentation attribute exists for it). The `--oc-*` properties are not emitted: nothing in the output references them once every class rule is inlined |
   | `.oc-chrome { font-family }` | Inherited from the root attribute |
   | `.oc-eyebrow { font-size, font-weight, letter-spacing, text-transform: uppercase, fill: accent }` | `font-size`, `font-weight`, `letter-spacing`, `fill` attributes; `style="text-transform: uppercase"` (no presentation attribute) |
   | `.oc-title`, `.oc-subtitle`, `.oc-source, .oc-byline, .oc-footer` (font-size, weight, fill) | Already inline: `applyTextStyle` writes `fill`, `font-size`, `font-weight`, `font-family` through `.style` on every chrome text node. No change |
   | `.oc-brand { 11px, 500, letter-spacing, fill: faint }` | Attributes on the brand text |
   | `.oc-eyebrow-dot { fill: accent }` | `fill` attribute on the dot |
   | `.oc-metrics { font-family }`, `.oc-metric-label { 11px, 500, letter-spacing, uppercase, fill: muted }`, `.oc-metric-value { 22px, 600, letter-spacing, fill: text, tabular-nums }`, `.oc-metric-delta-up/down { fill: positive/negative, 12px, 500 }`, `.oc-metric-secondary { fill: muted, 12px, 400 }` | Attributes on each metric text; `style` for `text-transform` and `font-variant-numeric` |
   | `.oc-axis-tick-inline { 11px, 400, fill: muted }` | Attributes on inline tick labels |
   | `.oc-endpoint-labels { font-family }`, `.oc-endpoint-label { fill: var(--oc-endpoint-label-color, text) }`, `.oc-endpoint-value { fill: var(--oc-endpoint-value-color, muted) }`, `.oc-endpoint-leader { stroke: var(--oc-endpoint-leader-color, currentColor) }` | `fill`/`stroke` attributes with the resolved fallback colors (`colors.text`, `colors.axis`, the series color for the leader) |
   | `.oc-annotation-subtitle { fill: var(--oc-annotation-subtitle-color, muted) }` | `fill` attribute |
   | `.oc-legend { font-family, font-size: body }`, `.oc-legend text { fill: legend-text }` | `font-size` on the legend group, `fill` on each legend text |
   | `.oc-legend-entry { cursor: default }` | Dropped (no pointer in static output) |

   The two `static.test.ts` cases that assert the block (`scopes custom properties to svg.oc-chart, not :root`, `uses var() references in class rules for theme overridability`) are deleted with that reason in the commit. What is lost: a host could restyle rc.2 static output by setting `--oc-*` on an ancestor; after U1 the only theme input for static output is the `theme` option at render time (R1, §7.13). The live mount path keeps the block for downloads (`export.ts::injectThemeStyleBlock`) and `chrome.css`, unchanged.

3. **Maps and tilemaps** keep a style block because their renderers rely on `.oc-map-label` hover and viewport classes. With an `idPrefix` the block's selectors are prefixed `#<idPrefix>-oc-root `; without one the block is emitted exactly as today. `docs/static-rendering.md` says a page with several static maps must pass distinct prefixes.

4. **Interactive affordances off at the source.** With `ctx.interactive === false`:
   - `renderers/legend.ts` emits legend entries without `role="button"`, `tabindex` and the pressed state; the group keeps `role="group"` and its text.
   - `renderers/annotations.ts` keeps the note marker (the numbered dot that replaces a label demoted by auto-thinning is the only visual link to its footnote) with `data-note-marker-index` and `data-note-spec-index`, and omits `tabindex`, `role="button"` and the "Activate to read the note" sentence from its `aria-label` (the label keeps `Annotation N: <text>`).
   - `renderers/chrome.ts` emits footnotes without `tabindex`; `role="list"`/`listitem` stay (they are structure, not interaction).
   - no `oc-animate` class, no `data-animation-*` attributes, no `<animate>`.
   A static test asserts `[tabindex], [role="button"], .oc-animate, animate` is empty for a chart with a legend, thinned annotations and footnotes, and that `[data-note-marker-index]` is non-empty for it.

5. **Role and name.** Unchanged: `role="img"` and `aria-label = a11y.description ?? generated` on the root (`compile/accessibility.ts::buildChartA11y`); `a11y.hidden` gives `aria-hidden="true"` and no role, which in-table cells use (§8). No `aria-describedby` is emitted in static chart output, so the site's finding sentence is the whole name. Static output never emitted a screen-reader table; the docs said otherwise and U13 corrects them. Because children of a `role="img"` element are presentational, per-mark `aria-label` in static output reaches nothing but pointer tooltips and DOM tests; static output therefore stops writing per-mark `aria-label` (R11) and relies on `<title>` (§7.3). Live mounts keep `aria-label` because `wireKeyboardNav` turns the root into a `group` and focuses marks.

Theming: no new token. Size: measured in U1 on the static fixture set and recorded in the PR (§10).

### 7.3 `encoding.description`, `data-mark` and identity attributes (G6)

Vega-Lite has a `description` channel ("a text description of this mark for ARIA accessibility"); OpenChart adopts it with the same name, as a field reference or a constant, and renders it as the mark's `aria-label` on live mounts and as a `<title>` child in static output.

Spec surface (`core/src/types/spec.ts::Encoding`, `BarListEncoding`):

```ts
description?: EncodingChannel;   // { field, format? } or { value: string }
```

`MARK_ENCODING_RULES` admits `description` as optional on every data mark. Field values are formatted through `resolveFieldFormatter` like `tooltip`; no template form (the site builds the exact string in its data).

Engine: `Mark` (every layout mark type in `core/src/types/layout.ts`) gains two optional fields filled by `charts/_shared` from the row at compute time: `markType: MarkType` (the spec mark that produced it) and `identity: Record<string, string>`. `MarkAria.label` is set from `description` when present, otherwise from today's generated text per chart module; `MarkAria.description` keeps its type and meaning (it is public) and is not used by this design.

**Series-level descriptions.** A line path or an area band is one element over many rows. Its `<title>` is the series description: `description.value` when constant, or the field's value when every row in the series shares one value (the site puts the series text on each row); when rows of a series disagree, the path gets no `<title>` and a `CompileWarning` names the series. Per-row dots from `point` take their own row's description.

**Where `data-mark`, identity attributes and `<title>` go.** Always on the shape element (the one with geometry attributes), never on a wrapper `<g>`; `aria-label`, `aria-hidden`, `data-series` and `data-mark-id` stay where `renderMarks` puts them today (the element each renderer returns). Decorative marks (`aria.decorative`) carry none of the three, so `[4.2f#19a]` never meets an element without a `<title>`.

| Layout mark | Produced by | Element that carries `data-mark`, identity, `<title>` | `data-mark` value |
| --- | --- | --- | --- |
| `RectMark` | `bar`, `rect`, `histogram`, `waffle` cells, `calendar` cells | the `<rect>`, or the `<path>` when `partialCorners` applies (stacked segment with a corner radius) | the spec mark: `bar`, `rect`, `histogram`, `waffle`, `calendar` |
| `LineMark` | `line` (one per series); `density` curves | the series `<path>`; none when the series has no segment of two or more points (§7.5) | `line`, `density` |
| `AreaMark` | `area`, `density` fills | the `<path>` | `area`, `density` |
| `ArcMark` | `arc`, `parliament` seats | the `<path>` | `arc`, `parliament` |
| `PointMark` | `point`, `beeswarm`, `lollipop` heads, `range` dumbbell heads, a `line`'s `point` dots, isolated line points (§7.5) | the `<circle>` | `point`, `beeswarm`, `lollipop`; `point` for a line's dots and isolated points; none for dumbbell heads (decorative) |
| `RuleMarkLayout` | `rule`, `lollipop` stems, `range` connectors, `errorbar` whiskers | the `<line>` | `rule`; `range` for connectors and `style: 'bar'` spans; `errorbar` for whiskers; none for lollipop stems (decorative) |

Identity attributes:

| Attribute | Value | Rule |
| --- | --- | --- |
| `data-<field>` | the row's value for the categorical or temporal position field (x, or y for horizontal marks), the `color` field, the `detail` field and `encoding.key` | The attribute name is the field name lower-cased with any character outside `[a-z0-9-]` replaced by `-`; if the result collides with a reserved suffix (`mark`, `mark-id`, `series`, `key`, `theme`, `display`, `animation-index`, `row-index`, `navigation-key`, `note-marker-index`, `note-spec-index`) it is prefixed `field-`. For the dot plot, `data-agent="codex"` on the `point` and on the `errorbar` whisker. A row whose value is `null` produces no mark, which is `[4.2f#6]`.

Static `<title>`: `renderMarks` with `ctx.interactive === false` inserts `<title>` as the first child of the shape element (SVG 2 wants it first for tooltips and AT) with the description text verbatim, escaped by the serializer. ### 7.4 The `errorbar` mark (G7)

A point estimate with an explicit interval, on either axis. Vega-Lite's composite is `errorbar` with `extent`; OpenChart takes the name and the explicit-bounds form only: the spec supplies `lower` and `upper` through `x`/`x2` (horizontal) or `y`/`y2` (vertical), and the estimate is a separate `point` layer. This follows the project's rule that intervals are never synthesized (`FieldMetadata.interval` doc) and keeps the mark a primitive like `range`.

Spec:

```ts
type MarkType = … | 'errorbar';
interface MarkOptions { …; ticks?: boolean }   // compiler/mark-options.ts::APPLIES_TO.ticks = ['errorbar']; default false
```

`strokeWidth` and `opacity` already exist on `MarkOptions`; the defaults for this mark are constants in `engine/src/charts/errorbar/constants.ts` (`ERRORBAR_STROKE_WIDTH = 2`, `ERRORBAR_CAP_LENGTH = 6`, `ERRORBAR_OPACITY = 0.35`), the way `DEFAULT_POINT_RADIUS` lives in the engine; no theme token group is added (§7.11).

`MARK_ENCODING_RULES.errorbar`:

```ts
errorbar: {
  x:  required('quantitative', 'nominal', 'ordinal', 'temporal'),
  y:  required('quantitative', 'nominal', 'ordinal', 'temporal'),
  x2: optional('quantitative'),
  y2: optional('quantitative'),
  color: optional(), opacity: optional(), detail: optional(), description: optional(), tooltip: optional(), key: optional(),
}
```

`compiler/validation/mark-rules.ts::validateErrorbarSpec` (beside `validateRangeSpec`, wired in `compiler/validation/chart.ts`): exactly one of `x2`/`y2`; the paired channel is quantitative; the other is nominal, ordinal or temporal. A row with `null` in either bound produces no mark.

Engine: `engine/src/charts/errorbar/` copied from `charts/range/`. `computeErrorbarMarks` emits, per row, one `RuleMarkLayout` from `scale(lower)` to `scale(upper)` at the band center and, with `ticks: true`, two decorative `TickMarkLayout`s of `ERRORBAR_CAP_LENGTH` at each end. The quantitative scale's domain unions `x2`/`y2` where `layout/scales.ts` already does so for `range` (the union lives there, not in `compile/chart-scales.ts`), so a `[0, 1]` interval at 0% and 100% lands on the plot edge. Color from the `color` channel or the primary series color; marks carry `data-mark="errorbar"` and identity attributes; the whisker `<line>` has `x1 x2` (or `y1 y2`), which satisfies `[4.2f#23]` once its selector reads `[data-mark='errorbar']`.

Sparkline mode: `applySparklineDefaults` leaves `errorbar` strokes alone (no trend color); the pad (§7.6) reserves the cap length and the layered point radius at both ends.

Rendering: nothing new; `RuleMarkLayout` and `TickMarkLayout` already render through `renderers/marks.ts`. Legend: no swatch (like `rule`). Tooltip and keyboard: the `point` layer carries them; whisker marks are `decorative: false` with `aria.label` from `description` or `"<category>: <lower> to <upper>"`.

Why not `point` with an `interval` option: it would be the first mark whose geometry comes from two extra channels hidden behind an option, and the dot plot needs the whisker under the dot in z-order, which layering gives. Why not `range` with `style: 'whisker'`: `range` carries `colorByDirection` and arrow semantics that do not apply, and its validation forbids a third position.

Docs: `chart-types.md` (with the "interval not synthesized" sentence and the no-`extent` note, Q4), `spec-reference.md` mark table and encoding-by-type table, `ranking-and-change.md` dot-plot section, `llms-full.txt` regenerated. Gallery: `examples/src/testing/fixtures-stats.stories.tsx` (horizontal by category, vertical over time, layered with `point`, sparkline cell) and the static fixture set.

### 7.5 One-point series and gap semantics (G8)

`computeLineMarks` emits one `LineMark` per series whose path joins every non-null segment with a new `M`; a one-point segment is a zero-length subpath, which `stroke-linecap: round` draws as a dot by accident; `renderLineMark` draws the `<path>` only when `points.length > 1`, so a one-point series renders an empty `<g>` that would still carry a `LineMark`. The site's `[4.2f#24]` wants a lone published point as `data-mark="point"` with no `data-mark="line"`.

Design: segments with one defined point are dropped from the path string and emitted as `PointMark`s (`DEFAULT_POINT_RADIUS`, the series color, `markType: 'point'`, the row's description, `decorative: false`), regardless of the `point` option, unless `point === false` is set explicitly, in which case nothing is drawn and a `CompileWarning` names the series and index. When no segment has two or more points, no `LineMark` is emitted at all. The isolated `PointMark` carries its row so `tooltipDescriptors` and keyboard navigation include it on the island (today both come from `LineMark.dataPoints`; the point path already feeds them for `point` charts). `area.ts` gets the same rule for its line and emits no band for a one-point segment. `density`, `histogram` and `calendar` are unaffected.

Sparkline pad: `getSparklinePad` stays private and keeps its stroke pad and 4 px dot pad; it gains the errorbar cap half-length and the point radius when `point` is set and the radius exceeds 3.5, and `compileLayer` computes the pad as the union over all leaves before freezing the budget (`frozenBudget` is taken from leaf 0 today, so a `point` layer under an `errorbar` layer would otherwise clip its dot at 0% and 100%).

Intended output change (§12, R5): a series with an isolated point draws it as a real `PointMark` instead of a cap artifact (same position, radius from `DEFAULT_POINT_RADIUS` instead of half the stroke width). The `fixtures-line` gap stories are re-captured once, with plates.

### 7.6 Layers, explicit domains, temporal columns and fixed gutters (G9, G10, G16)

**Layers.** `LayerSpec` gains `display?: Display`, `a11y?: A11yConfig` and `frame?: FrameConfig`; `compile/layer.ts::buildPrimarySpec` forwards them to the primary spec (its key list is explicit, so nothing is forwarded by accident), `compileLayer` applies `applySparklineDefaults` to each leaf and the hidden-chrome frame to the layer, and the root gets `data-display="sparkline"`. Needed for the in-table rate mark (`errorbar` under `point`) and for `a11y.description` on the by-agent figure and `a11y.hidden` on in-table cells.

**Explicit domains.** `layout/scales.ts` already honors an explicit `scale.domain` exactly: every `nice()` call is guarded by `!channel.scale?.domain`. No change; U7 adds the two tests that make it contractual: (a) in sparkline mode two cells with domain `[0, 1]` place the same value at the same pixel; (b) an explicit nominal domain keeps a band for a category with no row or a `null` value (band count equals domain length, no mark for it), so a suppressed agent stays an empty row in alphabetical position.

**Columns on a continuous temporal scale.** Today a `bar` with a temporal `x` compiles to nothing (§4, "Columns on time"). Design, in the grammar's own terms:

- `EncodingChannel` gains `interval?: 'day' | 'week' | 'month' | 'quarter' | 'year' | number` (milliseconds when numeric), valid on a temporal position channel of `bar`, `rect` and `errorbar`. When omitted for a temporal-x `bar`, the engine infers it as the smallest positive difference between distinct `x` values (one week for weekly data) and records the inference as a `CompileWarning` only when the differences are not all multiples of the inferred value.
- `computeColumnMarks` gains a continuous branch: for a time/utc `xScale`, each column spans `[scale(t) − w/2, scale(t) + w/2]` with `w = (scale(t + interval) − scale(t)) × (1 − padding)` and `padding` from `scale.padding` (default `0.2`, the band default); stacking goes through `layout/stack.ts` unchanged (it stacks by x key, which is the date string).
- The temporal scale's default domain extends by half an interval on each side (`layout/scales.ts`, the temporal builder) so the first and last columns are whole; an explicit `scale.domain` is honored as given.
- Reference lines need nothing new: `resolvePosition`'s `time`/`utc` branch already places a date, which is why the design keeps the history and the columns on the same scale type instead of moving the history to a band scale (Q12).
- Horizontal bars with a temporal `y` get the same branch in `charts/bar/compute.ts`.

**Fixed gutters.** The stack page stacks the history line chart over the weekly column chart and the plan requires one x axis. Two charts align when their plot rectangles share left and right edges and their x scales share a domain. Design: `frame?: { left?: number; right?: number }` on `BaseChartSpec` and `LayerSpec` (CSS px). `layout/frame.ts::createFrame` uses the given values for `FrameMeasures.leftGutter` and the right reserve instead of the measured ones. Precedence when a fixed gutter meets a reserve that wants more room (Q13):

| Reserve | Behavior under a smaller fixed gutter |
| --- | --- |
| Y tick labels | Shortened by a new `layout/axes/fit-labels.ts::fitAxisLabels` (the measure function, then an ellipsis; today no `labelLimit` option exists), one `CompileWarning` |
| Endpoint labels | Fit inside `frame.right` when the lane allows; otherwise demoted exactly as the narrow-lane path does today (`FrameMeasures.endpointLabelsDemoted`, legend fallback) |
| Outside refline labels | Fit inside `frame.right`; otherwise the existing fallback to inside placement with its diagnostic |
| Axis title header, size legend | Unaffected (they use vertical space) |

The fixed value always wins, so two charts with the same `frame` and the same explicit x domain have identical `ChartLayout.area.x` and `area.width`. The site sets both charts' `frame` to constants and the same `scale.domain`; the two numbers are not read back from a render (`renderStaticSVG` returns a string; a host that wants the measured gutter can call `@opendata-ai/openchart-engine`'s `compileChart` and read `area`, but the constants are the recommended route). `frame.top`/`bottom` are not added (Q6).

Docs: `spec-reference.md` (Display, Frame, `interval`), `dashboards.md` sparkline section, a "Two charts on one x axis" recipe in `static-rendering.md`. Gallery: `static/aligned-pair` and `bar/temporal-columns` stories.

### 7.7 Static `barlist` with groups, sort, domain, reference lines, labels and a11y (G11)

`barlist` renders an `<svg role="list">` of `role="listitem"` rows (`barlist-renderer.ts::renderBarListSVG`), compiled by `compile-barlist.ts` (descending sort, `maxItems`, `ellipsize`, a silent cap to `maxFittingRows` for the given height, alt text `Bar list showing N items ranked by <field>`). It is reachable only through `mountBarList`.

Spec (`BarListSpec`, `BarListEncoding`):

| Addition | Type | Meaning |
| --- | --- | --- |
| `encoding.group` | `EncodingChannel` (nominal) | Rows grouped in first-seen order; each group after the first gets a 1 px rule (`colors.neutral.border`) and a header row with the group label in `colors.neutral.secondary` |
| `encoding.description` | `EncodingChannel` | Per-row description, as §7.3; default `"<label>: <formatted value>"` |
| `sort` | `'descending' \| 'ascending' \| null` | Default `'descending'` (today); `null` keeps data order within a group. `maxItems` applies after sort, across the list |
| `encoding.value.scale.domain` | `[number, number]` | Fixed value axis; default `[0, max]` |
| `annotations` | `RefLineAnnotation[]` restricted to `x` | A vertical rule across all rows at the value, `label` above the first row, `style: 'dashed'` honored |
| `labels` | `Pick<LabelConfig, 'format' \| 'prefix' \| 'suffix'>` | Applied to the value text (today only `encoding.value.format` is read) |
| `a11y` | `A11yConfig` | `description` replaces the generated alt text; `hidden` as for charts |
| `height` (existing option) | `number \| 'auto'` | Static default `'auto'`: the compiled height is `rows × rowHeight + group headers + chrome + padding`, so no row is dropped. With an explicit height that cannot fit every row the compile emits a `CompileWarning` naming the dropped count instead of capping silently |

Static: `renderStaticSVG` dispatches `isBarListSpec` → `compileBarList` → `renderBarListSVG(layout, { ctx })`. In static output the root is `role="img"` with `aria-label` from `a11y.description ?? generated` and the rows are plain `<g>` (no `role="list"`/`listitem`: a list role with no focusable rows announces a count and then nothing navigable, Q11); the track's `fill="currentColor"` becomes the resolved color so the output is self-contained; each bar `<rect>` gains `data-mark="bar"`, `data-<label-field>` and `<title>` from `description`; a truncated label's `<title>` holds the whole label, so `[4.2f#21]` and `[4.2f#19a]` both hold. Live mounts keep `role="list"`.

Wrappers: `BarList` components already exist; the new fields are spec fields. Docs: the bar-list section (`ranking-and-change.md`), `static-rendering.md` types table. Gallery: grouped and reference-line variants; `static/barlist` fixtures.

### 7.8 `labels.content` for bars and ranges; stacked-column series labels (G12)

`LabelConfig` gains `content?: EndpointLabelContent` (`'label' | 'value' | 'label value'`; default `'value'`). For bars, `'label'` is the `color` series name when stacked or grouped and the category otherwise; `charts/bar/labels.ts` composes the string before its fit test, so `placement: 'inside'` with `'label value'` gives the mocks' `v1 85%` in each segment, colored by `contrast.ts::pickLabelColor` as today. For `range`, `'label'` is the channel title of each end (`encoding.x.title`, `encoding.x2.title`, falling back to the field names), so the time-to-green strip reads `median 14m` and `p75 26m` (`charts/range/compute.ts` emits each end's label today with the value only).

Stacked columns get direct series labels: `endpointLabels` is accepted on vertical stacked `bar` and renders each series' name beside its topmost segment in the last column, in the right-hand lane the line chart uses; collision resolution and the legend fallback come from `legend/suppression.ts` and `FrameMeasures.endpointLabelsDemoted`.

Docs: `spec-reference.md` Labels and Endpoint labels. Gallery: `bar` and `range` label stories gain `content` variants; existing baselines are unchanged because the default is `'value'`.

### 7.9 Live mounts: `data-theme`, `a11y.table`, `onMarkFocus` (G13)

`mount.ts` toggles `oc-dark` on the container; the SVG itself carries no theme attribute. Design: `svg-renderer.ts::renderChartSVG` stamps `data-theme` from `layout.theme.isDark`, so static and live output agree and the attribute survives re-renders.

Table opt-out: `A11yConfig` gains `table?: boolean` (default `true`). `mount.ts` builds the screen-reader table when `!hidden && table !== false` and wires keyboard navigation when `!hidden` as today, so a host that renders its own `<details>` table (the site) drops the duplicate without losing `[tabindex='0']` and arrow keys. `a11y.hidden` keeps its current meaning.

Keyboard focus event: `ChartEventHandlers.onMarkFocus?: (event: MarkFocusEvent) => void` with

```ts
interface MarkFocusEvent {
  datum: DataRow; series?: string; key: string; description?: string;
  element: SVGElement; event: FocusEvent | KeyboardEvent;
}
```

`MarkEvent` is not widened (its `event` is a `MouseEvent` and click/hover consumers depend on that). `wireKeyboardNav` and `wireMarkNavigation` take an options object with `onFocus`, called whenever the focused mark changes, including the first focus on Tab. React, Vue and Svelte wrappers add the prop/emit with the three `'interaction mode and listener parity'` blocks extended. OpenChart adds no live region: a chart cannot know whether the host has one, and two announcements are worse than none.

Reduced motion: entrance animation is disabled by `styles.css`'s `prefers-reduced-motion` rules; the check that `getAnimations({ subtree: true })` is empty lives in a new Playwright spec outside the visual baselines (`e2e/a11y/reduced-motion.spec.ts`), because `.claude/rules/visual-regression.md` forbids `emulateMedia({ reducedMotion })` in the baseline suite.

### 7.10 Default light palette (G14, approval-gated)

Measured in §6: `#06b6d4` (2.43:1) and `#e29e47` (2.28:1) fail WCAG 1.4.11's 3:1 against white, and `#a584dc` (2.90:1) fails against `#fafafa`; the dark palette passes everywhere. Three choices:

| Option | Effect | Recommendation |
| --- | --- | --- |
| A. Retune the three light colors to ≥3.2:1 on `#fafafa` while keeping hue order and ΔE between neighbors ≥ 20 (`#0891b2` is 3.53:1 and keeps the cyan; an ochre near `#b8780f` and a violet near `#8b6ad0` are plate candidates) | Every existing light chart with ≥1 series changes color slightly; all visual baselines re-captured once | Recommended, in the major, with before/after plates |
| B. Keep the palette, promote the `a11y-warnings.ts` contrast gate from `dev: true` to always-on warnings | No visual change; every default chart warns | Not recommended: a default that warns about itself |
| C. Keep the palette; document that hosts needing 1.4.11 pass `theme.palette` | No change | Acceptable fallback; the consuming site passes its own palette either way |

Whatever the decision, U12 adds `core/src/colors/__tests__/palette-contrast.test.ts` asserting each categorical color's ratio against the light and dark `colors.background` and surface values, so a future palette edit cannot regress silently; under option C the light rows are `test.skip` with the ratio in the name.

### 7.11 Theming

No new theme tokens. The design reads existing `ResolvedTheme` fields: `isDark` for `data-theme`; `colors.text`, `colors.axis`, `colors.neutral.secondary`, `colors.neutral.border`, `colors.neutral.faint`, `colors.gridline`, `colors.positive`/`negative`, `fonts.family`, `fonts.sizes.*` and `chrome.*` for the inlined chrome styles (§7.2). The mocks' `--od-*` variables map onto the existing fields through the `theme` option; nothing new is required for the site.

### 7.13 Migration notes for 9.0

- `renderStaticSVG` no longer needs `happy-dom`; a host that installed it only for OpenChart can remove it. Hosts that serialized calls through a mutex can stop.
- `renderChartSVG(layout, container, options)` and `registerMarkRenderer` (`MarkRenderer<T> = (mark, index, ctx) => SVGElement`) take a `RenderContext`; a custom mark renderer must create elements through `ctx.factory`, because under the static path there is no `document` and `document.createElementNS` throws.
- `captureSvgIdState`, `restoreSvgIdState`, `resetSvgIdCounter`, `setMarkRenderState`, `resetMarkRenderState` are removed. `nextSvgId` remains as the page scope's function.
- Static chart output: no `<style>` in `<defs>` and no `--oc-*` custom properties, so an ancestor's `--oc-*` overrides no longer affect it (theme through the `theme` option); `data-theme` and (with `idPrefix`) `id="<idPrefix>-oc-root"` on the root; `<title>` on marks when `description` is set; `data-mark` and identity attributes on every data mark's shape element; no per-mark `aria-label`; coordinates at three decimals; U+00A0 written literally. A host that diffed static output byte for byte re-baselines once (§12 lists every change).
- `role="button"`/`tabindex` on static legends, footnotes and note markers are gone; a host that styled them by those attributes switches to the `.oc-legend`/`.oc-footnotes` classes.
- An isolated point in a line series is a `PointMark` (§7.5).
- `bar` with a temporal `x` renders (it compiled to nothing before); a host that relied on an empty result by accident sees columns.

**Release boundary.** Merging to `main` publishes nothing. Per `.claude/rules/releasing.md`, a release is cut by hand with `node scripts/release.mjs <version>`; a version containing `-` publishes under the npm `next` dist-tag, which is the tag the site installs. The script copies the changelog section whose heading matches the version exactly, so each unit writes its lines under `## [Unreleased]` and the release-preparation PR renames that heading to `## [9.0.0-rc.N] - <date>` (with the one-paragraph intro the rc.2 entry has) before the cut. Three cuts are planned; the implementing agent opens each release-preparation PR when the listed units are on `main`, and the maintainer (the one with the GitHub API token the script needs for signed tags) runs the script after reviewing it:

| Cut | After | Heading | Why then |
| --- | --- | --- | --- |
| `9.0.0-rc.3` | U0, U1, U2, U4, U5, U7, U6 | `## [9.0.0-rc.3]` | The site's in-table marks and dot plots can be built against `next` |

## 14. What this RFC may get wrong

- The claim that no static-path renderer reads layout back from the DOM was checked by grep for `getBBox`, `getComputedTextLength`, `getBoundingClientRect` and `getComputedStyle` under `vanilla/src`; all hits are in mount, export or interaction modules. If U3 finds a renderer that does read back, that renderer takes a measurement function from the context rather than reinstating a DOM.
- The serializer contract is written against happy-dom 20.8's `XMLSerializer` (self-closing empty elements, namespace attributes first, its attribute and text escaping). If the parity test finds another systematic difference, it is normalized in the test and recorded in §12, and U1's goldens remain the contract.
- The list of `.style` write sites on the static path (§7.1) comes from a grep for `.style.` in the renderer modules; the proxy on `StaticElement.style` covers any missed site, and the grep test makes a new one visible.
- `applySparklineDefaults`, `compiler/sparkline-defaults.ts`, `layout/plan.ts` and `frame.ts` all branch on `display`; U7 must route the layer case through each of them.
- The interval inference for temporal columns (smallest positive difference between distinct x values) is a design choice; if real data has irregular weeks the `CompileWarning` fires and the site sets `interval: 'week'` explicitly, which §8 already does.
- The size targets (80,000 bytes for the stack page's chart share) are estimates until `scripts/static-budget.ts` measures them in U1; the number in the PR is the measured one.
- The site's wire schema may name fields differently from §8 (`sample` for `n`, `day` or `week` for the temporal field); identity attributes follow the real names, and the site's selectors follow its own fixtures.
